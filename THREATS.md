# Анализ угроз и защита в системе аутентификации Fittology

Ниже — угрозы, актуальные для механизма входа по логину/паролю, и то, как каждая из них
закрыта в текущей реализации (см. `routes/auth.js`, `server.js`, `middleware/requireAuth.js`).

## 1. Хранение паролей в открытом виде
**Угроза:** если база данных попадёт в чужие руки (утечка, кража бэкапа), а пароли хранятся
как обычный текст — злоумышленник сразу получает доступ ко всем аккаунтам, а заодно и к другим
сервисам, где пользователи повторно используют тот же пароль.

**Защита:** пароли никогда не хранятся и не логируются в открытом виде. При регистрации
пароль хэшируется алгоритмом **Argon2id** (`argon2.hash(password, { type: argon2id,
memoryCost: 19456, timeCost: 3, parallelism: 1 })`) — победителем Password Hashing
Competition (2015) и текущей рекомендацией OWASP для хэширования паролей. Библиотека сама
генерирует случайную соль для каждого пользователя и встраивает её (вместе со всеми
параметрами) в сам хэш. При входе исходный пароль не восстанавливается — сравнивается хэш
через `argon2.verify()`. В отличие от bcrypt, Argon2 дорог не только по процессорному
времени, но и по **памяти** (19 МБ на каждую попытку) — это специально затрудняет перебор
на GPU/ASIC-фермах, которые эффективны для дешёвых параллельных вычислений, но не для
дешёвой параллельной памяти.

## 2. Перебор пароля (brute force / credential stuffing)
**Угроза:** автоматический подбор пароля большим числом запросов к `/api/login`.

**Защита:** `express-rate-limit` ограничивает `/api/login` до 5 попыток с одного IP за 10 минут
(и отдельно `/api/register` — 10 попыток в час, чтобы нельзя было массово плодить аккаунты).
Дополнительно ответ на неверный логин и неверный пароль всегда одинаковый
(«Неверный логин или пароль»), чтобы нельзя было через разницу в ответах узнавать, какие логины
вообще существуют в системе (user enumeration).

## 3. Timing-атака при входе
**Угроза:** если для несуществующего логина сервер отвечает мгновенно, а для существующего —
с задержкой на argon2.verify, по времени ответа можно вычислить, какие логины зарегистрированы.

**Защита:** если пользователь не найден, сервер всё равно выполняет `argon2.verify` с
заранее посчитанным хэшем-пустышкой, чтобы время ответа не отличалось от случая с неверным
паролем (проверено замером: ~91 мс для несуществующего логина против ~83 мс для существующего
с неверным паролем — разница в пределах обычного сетевого джиттера, а не показательная).

## 4. SQL-инъекция
**Угроза:** внедрение SQL-кода через поле логина/пароля (например `' OR '1'='1`), если запрос
собирается склейкой строк.

**Защита:** все запросы к SQLite выполняются через параметризованные запросы
`better-sqlite3` (`db.prepare('... WHERE username = ?').get(username)`), где значения никогда
не подставляются в текст SQL-запроса напрямую.

## 5. XSS (Cross-Site Scripting)
**Угроза:** если имя пользователя выводится на страницу без экранирования, через него можно
внедрить `<script>` и, например, украсть данные другого пользователя, открывшего страницу.

**Защита:**
- Логин при регистрации ограничен regex-проверкой (`^[a-zA-Z0-9_]{3,20}$`) — спецсимволы и теги
  просто не проходят валидацию.
- На фронтенде (`auth-ui.js`) имя пользователя вставляется в DOM через `textContent`, а не
  напрямую в HTML-разметку — браузер не интерпретирует его как код.
- Cookie сессии помечена `httpOnly`, поэтому даже при успешной XSS-атаке в другом месте сайта
  украсть саму сессионную cookie через `document.cookie` нельзя.

## 6. CSRF (Cross-Site Request Forgery)
**Угроза:** сторонний сайт незаметно отправляет запрос (например, на смену данных) от имени
залогиненного пользователя, используя его же cookie.

**Защита:** cookie сессии выставлена с флагом `SameSite=Lax` — браузер не приложит её к
запросам, инициированным с чужого сайта. Для учебного проекта этого достаточно; в более
серьёзном проекте это дополняется CSRF-токеном на изменяющих операциях.

## 7. Перехват сессии / session fixation
**Угроза:** если ID сессии предсказуем или не обновляется при входе, его можно подставить
жертве заранее (fixation) либо перехватить и переиспользовать (session hijacking).

**Защита:**
- ID сессии генерируется `express-session` криптографически случайным и непредсказуем.
- При успешном логине сессия пересоздаётся (`req.session.regenerate`), поэтому старый ID,
  который мог быть известен атакующему до входа, после входа уже недействителен.
- Сессия ограничена по времени жизни (2 часа), после — нужно входить заново.

## 8. Перехват данных при передаче по сети
**Угроза:** при передаче логина/пароля по обычному HTTP трафик можно перехватить в открытом
виде (например, в общедоступном Wi-Fi).

**Защита:** в конфигурации cookie предусмотрен флаг `secure: true` для production-режима
(`NODE_ENV=production`), из-за которого cookie будет передаваться только по HTTPS. В реальном
развертывании перед сервером должен стоять HTTPS (например, через reverse-proxy с
TLS-сертификатом) — в учебном окружении на localhost это не включено намеренно, иначе браузер
не примет cookie без сертификата.

## 9. Clickjacking / MIME-sniffing
**Угроза:** встраивание страниц сайта в `<iframe>` на чужом сайте для обмана пользователя, либо
подмена типа контента браузером.

**Защита:** заголовки `X-Frame-Options: DENY` и `X-Content-Type-Options: nosniff`
устанавливаются для всех ответов сервера (см. `server.js`).

## 10. Слабый/предсказуемый пароль (словарная атака)
**Угроза:** Argon2 делает перебор *дорогим*, но не делает его *бессмысленным* — если пароль
попадает в список самых частых (`123456`, `password`, `qwerty` и т.п.), атакующему не нужен
перебор символов вообще: он проверяет буквально несколько тысяч известных вариантов и находит
совпадение за секунды. Технически это тот же самый механизм (argon2.verify), просто список
кандидатов сразу маленький и точный. Отдельный частный случай — так называемые
**клавиатурные паттерны** (`qwerty`, `1qaz2wsx`, `asdfgh`): визуально пароль выглядит сложным
(есть и буквы, и цифры), но на деле это одна из немногих "дорожек" пальца по клавиатуре, и
таких комбинаций конечное небольшое число — они тоже входят в любой словарь для брутфорса.

**Защита:** при регистрации (`checkPasswordStrength` в `routes/auth.js`) пароль проверяется
до хэширования по нескольким независимым правилам:
- отклоняется, если входит в список самых частых/утёкших паролей — используется npm-библиотека
  **`common-password`** (`data/common-passwords.js`), которая внутри опирается на тот же
  открытый исследовательский датасет SecLists (~10 000 паролей из реальных утечек данных),
  но хранит их не как открытый текст, а как CRC32-хэши — компактнее и сам список паролей не
  лежит в проекте текстовым файлом. Это тот же принцип, что использует, например, проверка
  Have I Been Pwned — сверка с базой уже скомпрометированных паролей. Поверх библиотеки
  добавлено небольшое ручное дополнение с русскими вариантами (`EXTRA_RU` в том же файле);
- отдельно детектируется **клавиатурный паттерн** (`data/keyboard-patterns.js`) —
  последовательность из 4+ символов подряд, стоящих рядом на раскладке (ряды qwerty/asdf/zxcv,
  цифровой ряд, диагонали типа `1qaz2wsx`, включая русскую раскладку). Эта проверка работает
  независимо от списка частых паролей — например, `rfvtgb99` не входит в датасет утечек, но
  всё равно отклоняется как клавиатурная дорожка;
- отклоняется, если совпадает с логином;
- отклоняется, если состоит только из цифр или из одного повторяющегося символа;
- обязательно должен содержать и буквы, и цифры.

Это не отменяет хэширование и rate limiting — они остаются защитой на случай, если пароль
всё же окажется предсказуемым каким-то другим образом. Требование к паролю сокращает набор
реалистичных вариантов для перебора, а Argon2 + rate limiting делают сам перебор медленным
и ограниченным по числу попыток. В сумме это и даёт практическую неуязвимость для типичной
атаки на страницу входа.

## 11. Replay-атака (повторная отправка перехваченного запроса)
**Угроза:** даже если данные входа зашифрованы (HTTPS) или их не удалось расшифровать,
атакующий может просто **скопировать и переслать позже** ровно тот же самый перехваченный
запрос на вход — серверу нечем отличить его от настоящего, если запрос сам по себе не несёт
информации о том, когда он был создан.

**Защита:** клиент добавляет в запрос на вход временную метку `timestamp: Date.now()`
(момент отправки). Сервер (`routes/auth.js`) сравнивает её с собственным текущим временем и
отклоняет запрос, если разница больше 2 минут — то есть повторно отправленный "старый" запрос
просто не пройдёт проверку.

**Честное ограничение (стоит проговорить на защите):** сама по себе метка времени не подписана
и не зашифрована — она лишь **сужает окно**, в течение которого повтор вообще технически
возможен (секунды-минуты вместо неограниченного времени), но не исключает его полностью внутри
этого окна. Полноценная защита от replay-атак требует дополнительно:
- одноразовый **nonce** — сервер запоминает уже использованные значения и отклоняет повтор
  даже в пределах окна;
- **HTTPS**, чтобы саму метку нельзя было подделать или подменить "на лету" при перехвате
  (см. угрозу №8 про перехват трафика — без шифрования канала эта защита сама по себе
  тоже уязвима).

## 12. Обход проверки прав на защищённой странице
**Угроза:** прямой запрос `GET /cards.html`, минуя интерфейс, в надежде, что защита есть только
на уровне ссылки в меню, а не на уровне сервера.

**Защита:** маршрут `/cards.html` обрабатывается middleware `requireAuth` **на сервере** до
того, как файл будет отдан — проверка не зависит от того, что показывает или скрывает
JavaScript в браузере. Без активной сессии запрос всегда получает редирект на `/login.html`.
